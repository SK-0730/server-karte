# サーバーカルテ 企画概要

> はじめてのサーバーに、はじめての健康診断

就職作品（2026年度後期）。初学者が自宅サーバーをパソコンのアプリから診断し、外部公開の前後にありがちな設定ミスに気づいて直せるようにするデスクトップアプリ。

- 元資料：1シート企画書（v2・2026/10/19）、機能一覧・システム構成図（2026/11/02）、WBS（11/5見直し）
- 開発の流れ・CI/CDは [DEVELOPMENT.md](DEVELOPMENT.md) を参照

---

## 1. 背景

ゼミ研究「初学者によるAI任せのサーバー構築のセキュリティ検証」で、目に見える脆弱性や問題が確認できた。

- 生成AIを使えば、IT知識が少なくてもWebアプリ開発やサーバー構築ができるようになった
- しかし、AIの指示を確かめずに従うと脆弱性を放置してしまうことがある
- 例：ゼミの検証範囲では、AIが示すサーバー構築手順に **ソフトウェアのアップデートを避ける傾向** が見られた。この手順どおりに作業すると、既知の脆弱性が修正されないまま公開されるおそれがある

既存ツールとの違い：

| ツール | 特徴 | 初学者にとっての課題 |
| --- | --- | --- |
| Lynis など | サーバー内部の設定を診断 | 管理者向け。コマンド操作が前提、結果が英語で項目も多い |
| Nmap / ZAP | 外部からポートやWebアプリを調査 | 公開前のサーバー内部の設定ミスを初学者向けに説明するものではない |

## 2. 問題点

1. 初学者は生成AIの手順をそのまま信じ、危険な設定に気づかないまま外部公開してしまう
2. 既存の診断ツールは管理者向けで、初学者には使いこなせない
3. 危ないと分かっても、なぜ危ないのか・どう直すのかが分からず対処できない

## 3. ターゲット

生成AIを活用して、自宅サーバーの構築・外部公開に挑戦する初学者（公開前・公開後のどちらも対象）

## 4. 解決案

1. **ボタンひとつで診断**：パソコンのアプリに接続情報を入力して押すだけ。コマンド操作は不要
2. **項目を絞って分かりやすく**：初学者に必要な項目（外部公開ポート、公開フォルダ内の不要ファイル、アップデート停止・古いソフト、SSH設定）に絞り、健康診断の結果票のようにA〜Eの判定とあわせて日本語で表示する。項目はゼミ研究で見つけたつまずきが元
3. **直し方まで案内**：項目ごとに「なぜ危ないのか」「どう直すのか」を説明し、生成AIに相談するための文面も用意する。直したあとに再診断して、直ったことを確かめられる

## 6. システム構成

### 利用者側（ローカル完結）

```
[利用者のPC]                              [利用者のサーバー]
 サーバーカルテ（Wails v2 / Windows exe）     Ubuntu + OpenSSH
  ├ 画面：React + TypeScript（Vite）  ─SSH─▶  診断コマンドを実行（読み取りのみ）
  ├ 診断処理：Go（SSH接続・解析）
  └ 診断履歴：SQLite（あれば良い）
```

### 開発・配布側

```
開発者 ─push/PR─▶ GitHub ─▶ GitHub Actions
                              ├ exe自動ビルド ─(タグ時)─▶ GitHub Releases ─▶ 利用者がDL
                              └ 紹介ページ ─▶ GHCR ─Tailscale─▶ prod（自宅Proxmox）
                                                               └ Cloudflare ─▶ 閲覧者
```

| 構成要素 | 使用技術 | 役割 |
| --- | --- | --- |
| アプリ本体 | Wails v2 | 受付・診断・結果表示。Windows用exeで配布 |
| 画面 | React（TypeScript）、Vite | 受付票・カルテ風の画面 |
| 診断処理 | Go | SSH接続、コマンド実行、結果の解析 |
| 診断履歴 | SQLite | 利用者のPC内に保存（あれば良い） |
| ソース管理 | GitHub（server-karte） | `app/`（アプリ）と `site/`（紹介ページ） |
| CI/CD | GitHub Actions | exe自動ビルド、紹介ページの自動デプロイ |
| exe配布 | GitHub Releases | タグ時のみ公開（あれば良い）。コード署名なし |
| イメージ置き場 | GHCR | 紹介ページのコンテナイメージ |
| デプロイ経路 | Tailscale | Actions から prod へ接続 |
| 本番環境 | 自宅Proxmox（prod VM） | 紹介ページを動かす |
| 公開経路 | Cloudflare | 紹介ページをインターネットに公開 |
| 開発環境 | 自宅Proxmox（dev VM） | アプリと紹介ページの開発 |
| 検証環境 | VirtualBox（patient01）、Ubuntu 20.04 | 診断の実験台（患者役）。ゼミ検証VMのクローン、ホストオンリーで隔離 |

## 7. 設計方針

| 方針 | 内容 |
| --- | --- |
| ローカル完結 | 診断結果や接続情報を外部に送らない。共有機能は作らない |
| 認証情報は保存しない | SSHのパスワード・鍵、sudoパスワードは受付のたびに入力 |
| 読み取りのみ | 診断は設定の読み取りだけ。サーバーの設定は変更しない |
| 自分のサーバーだけを診断 | 利用者自身が管理するサーバーのみ対象 |
| まずUbuntuに対応 | Ubuntu以外はスキップ。他OSは後回し |
| 鍵認証を勧める | パスワードログインも受け付けるが、結果で鍵認証への移行を勧める |
| コード署名はしない | 学生個人では取得が難しく費用も大きい。警告の理由と開き方を紹介ページで説明 |
| prodは検証に使わない | わざと穴を開ける検証は隔離した patient01 で行う |

前提条件：診断するサーバーにSSHで接続できること（導入方法は紹介ページに記載）

## 9. アピールポイント

**プロダクト視点**
- サーバー側へのインストールやコマンド操作が不要。接続情報を入れて「診断する」を押すだけ
- 気づく → 理由を理解する → 直す → 再診断で確かめる、まで一つのアプリで完結
- デモ：あえて危ない設定にしたサーバーを診断し、指摘に沿って直したあと、再診断で問題が消える様子を見せる

**技術視点**
- ゼミ研究で見つけた課題を作品で解決する、という一貫した流れ
- 各チェック項目は公式ドキュメント等で「なぜ危ないか」の根拠を確かめてから実装
- Lynisなど既存ツールを試したうえで、初学者に必要な項目へ絞った判断理由を示す
- 診断ツール自体が新たなリスクにならない設計（読み取りのみ・認証情報を保存/送信しない）

使用技術：Linuxセキュリティ設定（SSH、ファイアウォール、ポート、Docker、アップデート）、Go、React、Wails、Docker、Git、GitHub Actions
